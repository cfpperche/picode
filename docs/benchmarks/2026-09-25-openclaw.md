# Study: OpenClaw 2.0+, and whether PiCode should integrate it

- **Date:** 2026-09-25
- **Why now:** the owner asked whether PiCode should integrate OpenClaw
  2.0+. OpenClaw shows up in three studies (computer use, AGENTS.md, the
  skills marketplace's ClawHub record) and in ADR-0196, but it has never
  been the subject of a study.
- **Sources:** live reads of docs.openclaw.ai, the openclaw.ai blog and
  GitHub releases on this date; `npm view openclaw` and the GitHub REST
  API (repository stats, published repository advisories, the GitHub
  Advisory Database) queried on this date; press (InfoQ, MarkTechPost,
  Wikipedia) for context only; PiCode's tree at `feat/openclaw-study`.
- **Not measured:** OpenClaw was not installed or run. This machine has
  Node 24.11.1 and the package requires `>=24.16.0 <25 || >=26.1.0`, so
  every claim about the TUI, ACP or embedding comes from the docs and was
  not probed. Costs for doors C3–C5 are extrapolated from the Hermes
  footprint, not built.
- **In-house bars:** ADR-0069 (CLIs in terminals), ADR-0091 (managed mode
  is Pi's; ACP waits), ADR-0160 and ADR-0184 (a CLI launch is an agent; one
  door), ADR-0179 (every agent CLI is optional), ADR-0075 (webhooks),
  ADR-0154 (picode-mcp), ADR-0196 (skills).
- **Scope:** OpenClaw as something PiCode could host, supervise or talk to.
  Not OpenClaw as a personal assistant to adopt.

## Verdict

**Do not integrate OpenClaw as a catalog CLI or as a managed runtime.** The
only door worth opening is a connector recipe that needs no code (C1), and
only when the owner wants it. The reason, in one line: with 2.0 OpenClaw
stopped being an agent a host runs and became a browser control plane for
agents — PiCode's own layer — with a protocol that gives operator clients
no compatibility window, a release every ~3 days, and an authority model
PiCode's grants cannot see.

## The question, in PiCode terms

PiCode hosts coding-agent CLIs: nine catalog rows
(`internal/clilaunch/config.go:45`), each running its own TUI in a PiCode
terminal, plus one managed runtime (Pi over RPC, ADR-0091). "Integrate
OpenClaw" can mean six different things (C1–C6 below), with costs that
range from a docs page to a second product. Before any of them there is a
prior question: after 2.0, is OpenClaw a guest PiCode can host, or a host
of its own?

## A. A peer now, not a guest

What the 2.0 web UI ships ("The New Web UI" release page), next to what
PiCode already has:

| OpenClaw 2.0 Control UI | PiCode today |
|---|---|
| Sidebar grouped by project, person or custom group; worktrees fold into their project; live activity indicators | workspace sidebar, worktrees, agent activity |
| New Session: agent, model, reasoning, workspace, machine; a Place picker that creates a managed worktree | New agent through one door (ADR-0184) |
| Full-screen web terminal (a host PTY in the agent workspace, `operator.admin` only) | tmux terminals |
| Changes panel: branch commits, working-tree edits, PR status, CI summaries (read-only) | git graph and Changes |
| Browser panel: element inspection and annotation, screenshot markup | browser surface; the design-mode study ([2026-09-18](2026-09-18-annotation-design-mode.md)) |
| Desktop focus view | computer tool; the desktop shell's focus mode |
| Approvals inline and in an Inbox | Inbox ([ADR-0037](../decisions/0037-inbox-async-agent-human-messages.md)) |
| Swarm; the Workboard plugin (cards → `wb-<card-id>` worktrees → sub-agents) | fleet, Canvas, missions |
| Skill Workshop and ClawHub | Skills ([ADR-0196](../decisions/0196-skills-for-every-agent-cli.md)) |
| Dashboards with pinned MCP app views | workspace overview |
| PWA-style mobile tabs and drawer | mobile app |

Hosting OpenClaw as a PiCode agent therefore puts a host inside a host: two
supervisors, two permission models, two worktree managers, two credential
stores (2.0 adds its own secret store and a 1Password broker) and two skill
catalogs. PiCode's premise — the user controls the agent from the moment of
creation — stops at OpenClaw's boundary. What an OpenClaw agent may do is
set by OpenClaw's tool policy, exec approvals and channel allowlists, and
PiCode's grants (browser, computer, delivery;
[ADR-0143](../decisions/0143-terminal-agents-as-principals.md),
[ADR-0184](../decisions/0184-one-cli-door.md)) never see them.

The difference that survives the overlap: PiCode runs each CLI's own TUI,
while OpenClaw drives the same CLIs headless through ACP and the Codex
app-server.

## B. The security record (measured 2026-09-25)

| Measure | Value |
|---|---|
| Published repository advisories, 2026 | 722: 14 critical, 249 high, 390 medium, 69 low |
| By month | Jan 3 · Feb 220 · Mar 204 · Apr 108 · May 67 · Jun 45 · Jul 0 · Aug 0 · Sep 75 |
| 2026-09-11 alone | 75 (30 high, 40 medium, 5 low) |
| GitHub Advisory Database, reviewed, npm `openclaw` | 760 (26 critical, 266 high), 452 with a CVE id; the latest published in July |

The 2026-09-11 batch covers the exact bridge PiCode would sit on: "Claude
permission replies could omit owner authorization", "Codex bind could omit
owner authorization", "MCP configuration changes could omit owner
authorization", "Reusable exec approvals could authorize changed
arguments", "Exec approvals could outlive their reviewed working
directory" and "Gateway upgrade-like requests could retain unauthenticated
sockets". The critical advisories cluster in February–April; six of the
fourteen are pairing or scope escalations to `operator.admin`, three of
them reaching remote code execution on a node.

The trust model is explicit about its edge: one trust boundary per gateway
— one operator or a mutually trusting team; "Everyone who can message a
tool-enabled agent shares that agent's delegated tool authority";
`sessionKey` is a routing selector, not an authorization token;
adversarial users need separate gateways. 2.0 still stores secret-store
values unencrypted in `state/openclaw.sqlite`, protected by file mode
only, and leaves the sandbox off by default — The Register's criticism of
the release, confirmed by the secrets doc.

Outside the repository: tens of thousands of internet-exposed instances
(Censys confirmed 63,070 on 2026-03-31, per CyberDesserts); CVE-2026-25253,
token theft leading to remote code execution, fixed in 2026.1.29; the
ClawHub supply-chain campaigns already recorded in the
[skills-marketplace study](2026-09-23-skills-marketplace.md); and a March
2026 restriction on OpenClaw for China's state-run enterprises and
agencies (Wikipedia).

What this means for PiCode: the volume is also evidence of a disclosure
process that works — a project that publishes 75 advisories in a day is
looking for them. But anything PiCode exposes to an OpenClaw gateway is
reachable by whoever can message that gateway, and PiCode's principal
model has no way to express "the authority of a WhatsApp sender".

## C. Six doors, priced

### C1. A connector: `openclaw mcp serve`

A stdio MCP server backed by a running gateway (token or password auth).
Nine tools: `conversations_list`, `conversation_get`, `messages_read`,
`attachments_fetch`, `events_poll`, `events_wait`, `messages_send`,
`permissions_list_open` and `permissions_respond` (`allow-once`,
`allow-always`, `deny`). Claude Code also gets channel notifications
(`--claude-channel-mode on|auto`). PiCode already installs MCP servers per
CLI and scope ([integrations.md](../architecture/integrations.md)), so this
works today without code; the cost is a docs-site recipe. It gives a
PiCode agent the owner's channels and OpenClaw's approval queue — which is
also its risk: it is a way out of the fleet, chosen by the owner, per
agent.

### C2. PiCode → OpenClaw hooks (notifications in messengers)

`POST /hooks/agent` and `POST /hooks/wake` require `Authorization: Bearer
<token>` or `x-openclaw-token`, reject tokens in the query string and
document no signature verification. PiCode's webhooks send fixed headers only — `Content-Type`,
`User-Agent`, `X-Picode-Timestamp`, `X-Picode-Event-Id`,
`X-Picode-Event-Type` and `X-Picode-Signature`
(`internal/webhooks/engine.go:130`) — and refuse URL userinfo, so today
they cannot authenticate to a hook. Making it work means an optional
bearer token per subscription: a stored secret and a migration, which is a
persistence and security-model change amending
[ADR-0075](../decisions/0075-integrations.md). The value is reach into
messengers; the ask-and-answer round trip on the phone already exists
through the Inbox and picode-mcp
([ADR-0154](../decisions/0154-picode-mcp.md)).

### C3. A tenth catalog row, terminal only

`internal/clilaunch` keeps `SurfaceTerminal` for "a future CLI that needs
a terminal before its adapter exists" (`config.go:29`), and the row would
launch `openclaw tui`. But the TUI is a client of a gateway (`--url`,
`--token`) or, with `--local`, needs "exclusive state directory
ownership", so two agents cannot share it. It takes no project folder: it
picks an agent only when launched inside a configured OpenClaw agent
workspace, and `--session` defaults to `main`. Every PiCode "OpenClaw
agent", in any workspace, would talk to the owner's main session unless
PiCode invented session keys. Under ADR-0184 it would be an agent row with
no activity state and no sessions, standing in the fleet next to nine rows
that have both.

### C4. A full row, like Hermes

The anchor, measured in this tree: the Hermes-only files hold about 2,000
lines (`internal/clisession/hermes*.go`, `internal/clicreds/hermes_catalog.go`,
`internal/connectors/hermes.go`, `internal/climetrics/hermes.go`,
`internal/server/hermes_login.go`), 37 production Go files reference the
`"hermes"` id, and 50 commit messages mention Hermes. OpenClaw would cost
more: the session reader, exit insights and the cross-CLI handoff read
each CLI's files, and OpenClaw forbids that, so all three would need a
protocol v4 WebSocket client with device-signature auth (`chat.history`,
`sessions.list`, `usage.cost`).

### C5. Managed: PiCode supervises the gateway

The cleanest contract in the study. The embedding doc says: spawn
`openclaw gateway --allow-unconfigured` with `OPENCLAW_NO_RESPAWN=1`,
`OPENCLAW_DISABLE_BONJOUR=1`, `OPENCLAW_EXEC_SHELL_SNAPSHOT=0` and
optionally `OPENCLAW_SKIP_CHANNELS=1`; treat the protocol handshake
(`connect.challenge` → `connect` → `hello-ok`) as readiness, never the
logs; read the `shutdown` event's `restartExpectedMs` (close code 1012);
on exit 78 (`EX_CONFIG`) run `openclaw doctor --fix --yes
--non-interactive` and retry once; touch state only through RPC. 2.0 also
adds `OPENCLAW_SUPERVISOR_MODE=external`, so an outside supervisor owns
restarts and updates. Three things weigh against it. It is the managed
mode ADR-0091 keeps for Pi. Operator and UI clients must speak the current
protocol (v4) — the N-1 window is for nodes only — while releases land
every ~3 days. And what PiCode would build is a second Control UI for a
product that already ships one.

### C6. ACP: `openclaw acp`

A stdio ACP server bridged to a gateway session (`acp-bridge:<uuid>` by
default). It implements initialize, new session, prompt, cancel, list,
resume and close sessions, thought and tool-call updates, and
`session/set_mode`. It does not implement the client's `fs/*` or
`terminal/*` methods, and it rejects per-session `mcpServers`. Under a
future PiCode ACP client — the open question in
[acp-trigger.md](../handoff/open/acp-trigger.md) — OpenClaw would be a
chat-only agent that ignores PiCode's connectors. It does not count
toward ADR-0091's trigger, which is measured over the CLIs PiCode hosts.

### Summary

| Door | Gives PiCode | Cost | Verdict |
|---|---|---|---|
| C1 `mcp serve` connector | an agent reads and sends channel messages and answers OpenClaw approvals | a docs-site recipe | yes, when the owner wants it |
| C2 hooks | notifications into messengers | a bearer per webhook: migration plus an ADR-0075 amendment | only on demand |
| C3 terminal-only row | the TUI next to the agents | small: a catalog row and docs | no |
| C4 full row | parity with the other nine | more than Hermes (~2,000 lines, 37 files) plus a WebSocket client | no |
| C5 managed gateway | a first-class OpenClaw | a second Control UI in lockstep with protocol v4 | no |
| C6 ACP | a chat-only agent, if PiCode ever speaks ACP | nothing now | note it; do not build for it |

## D. Two facts that retire older assumptions

1. **The Pi link is gone.** Early-2026 write-ups describe OpenClaw
   embedding Pi's `createAgentSession()`. 2.0's runtime doc says no
   external agent framework remains, and npm lists only `pi-tui`. "OpenClaw
   is built on Pi" is no longer a reason for PiCode to host it — and under
   [ADR-0179](../decisions/0179-agent-clis-optional.md) Pi is one CLI among
   nine anyway.
2. **The category is already in the catalog.** Hermes Agent, the personal
   agent with a messaging gateway, is a full row, and it imports OpenClaw
   installs (`hermes claw migrate`). A user leaving OpenClaw has a path in
   PiCode today.

A third data point: NVIDIA OpenShell lists OpenClaw among its supported
agents, but "Blueprint-managed" inside NemoClaw rather than as a preset like
the coding CLIs. Another host treats it as a service to provision, not a
CLI to launch.

## What PiCode adapts

Patterns, not code:

- **Snapshot before removing a worktree.** A synthetic commit pinned at
  `refs/openclaw/snapshots/<id>`, restorable for 30 days,
  `worktrees remove --if-lossless`, and a 7-day idle collector. A
  candidate for PiCode's worktree removal and for agent history
  ([ADR-0205](../decisions/0205-agent-history-from-exits.md)).
- **Credentials that never enter the model's context.** A masked prompt
  for the value, and an egress proxy that substitutes a protected secret
  only for approved hosts and closes when the run ends. Input for step 2
  of the credentials vault ([2026-09-20](2026-09-20-agent-cli-credentials.md)).
- **Approvals bound to the exact request, command, session and person.**
  The advisories about reusable approvals and approvals that outlive their
  working directory are test cases for any PiCode approval that is ever
  reused.
- **The embedding contract's shape.** Readiness by handshake, and
  `EX_CONFIG` → repair → retry once → surface to the user: a reference for
  the desktop shell's supervision of the daemon.
- **The `agent exec --json` envelope.** `status`, `final`, `usage`,
  `costUsd`, `toolSummary`, exit codes 0/1/2: a reference shape for
  headless runs.

## What PiCode refuses

- **OpenClaw as a catalog CLI (C3, C4).** It is not a coding CLI in
  PiCode's sense but a host whose agents' authority PiCode cannot govern.
- **A managed OpenClaw runtime (C5).** Lockstep with protocol v4 and a
  ~3-day release train, to rebuild a UI OpenClaw already ships.
- **PiCode's control surface exposed to a gateway.** Agent launch and
  grants in reach of an OpenClaw agent would hand the fleet to whoever can
  message that gateway. The smallest thing that could ever be offered is
  an external principal limited to reading and answering the Inbox, and
  that is a security-model ADR, not a recipe.

## Open questions (owner)

- **C1:** publish the `openclaw mcp serve` connector recipe in docs-site?
  It needs no code and is the only cheap, reversible door.
- **C2:** is reach into WhatsApp or Telegram wanted? If so, choose between
  a bearer token on webhook subscriptions (an ADR-0075 amendment) and a
  channel PiCode owns.
- **Re-open triggers:** real demand to drive PiCode from a messenger;
  OpenClaw giving operator clients an N-1 protocol window or a versioned
  embedding contract; high and critical advisories staying low for a
  quarter; PiCode building an ACP client (then C6 comes almost free,
  chat-only).
