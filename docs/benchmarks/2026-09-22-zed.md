# Study: Zed's agent surface, and whether ACP's trigger has fired

- **Date:** 2026-09-22
- **Why now:** the owner keeps seeing Zed praised and asked what a study of
  it would buy PiCode. Zed is cited in nine ADRs and three studies but has
  never had a note of its own, so every past borrow was a one-line
  reference with no receipts behind it.
- **Sources:** live reads of zed.dev docs and blog on this date (each claim
  carries its URL in [Sources](#sources)); Zed's shipped
  `assets/settings/default.json` for values the docs leave out; the ACP
  site and registry; PiCode's own tree at `feat/zed-benchmark`.
- **In-house bars:** [benchmarks.md](../benchmarks.md) (UI/UX section, the
  Feel bar), ADR-0091 (the ACP refusal and its trigger), ADR-0089 (the
  prompt door), ADR-0069 (managed terminals for nine CLIs), ADR-0015 and
  [diff-editor-roadmap.md](../design/diff-editor-roadmap.md) (hunk review).
- **Scope:** Zed's *agent* surface and its performance posture. Not Zed as
  an editor — edit prediction, LSP, vim mode, CRDT collaboration and
  channels are out, and stay out (see [Refuses](#what-picode-refuses)).

## The question, in PiCode terms

Praise for Zed is usually about feel, not features: it opens fast and gets
out of the way. That is worth studying, but it is not transferable — Zed is
a Rust editor on a GPU renderer and PiCode is a Go server feeding a browser.
What *is* transferable is narrower and more useful:

1. Zed made the agent's edits reviewable in one place, across files.
2. Zed wrote its tool-permission model down as a precedence table.
3. Zed shipped an ACP client, so its registry is the honest place to
   re-measure ADR-0091's undated trigger.

## A. Zed's agent surface

### A1. Review Changes — one multibuffer for the whole turn

The panel keeps an accordion above the composer naming which files, how
many, and how many lines the agent edited. `Review Changes`
(<kbd>ctrl-shift-r</kbd>) opens a **multibuffer tab** holding every change,
one excerpt per file. There you accept or reject each hunk, or the whole
set. Zed ships the actions `agent: keep`, `keep all`, `reject`, `reject all`
and — the part worth stealing — **`undo last reject`**. A per-message
`Restore Checkpoint` button rewinds to before that model edit.

Multibuffers are not an agent invention: project search, diagnostics, find
references and Git's Project Diff (<kbd>ctrl-g d</kbd>, stage per hunk or
per file) all open the same widget. The agent review reuses a thing users
already know. `agent.single_file_review` (default `false`) moves the same
keep/reject controls inline into each file instead.

**The gap here is real.** PiCode reviews one card at a time because a card
is one tool call. A turn that edits six files is six cards in scroll order,
interleaved with prose, with no "this is everything that changed" view and
no way to accept the lot. The summary accordion is the cheap half: a line
above the composer saying *6 files · +142 −38* with the turn's basenames.

### A2. Follow the agent

A crosshair toggle at the panel's bottom left makes the editor jump to each
file the agent reads or edits; holding <kbd>cmd/ctrl</kbd> while submitting
turns it on for that message. One toggle, one behaviour, no settings page.

PiCode has the two halves already — a file pane (E1) and a feed that knows
which file each tool touched — and nothing joins them. This is the cheapest
item in the study and the most visible.

### A3. Permissions as a precedence table

Zed's tool-permission cards offer **Allow once**, **Deny once**, **Always
for `<tool>`**, and **Always for `<pattern>`**. The second "always" is the
interesting one: when a pattern can be safely extracted from the call, the
choice is persisted as a regex rule rather than a blanket grant, so
`git status` can be allowed without allowing every terminal command.

Resolution order, most specific first:

| Rank | Rule | Note |
|---|---|---|
| 1 | Built-in security rules | terminal only (`rm -rf /`, `/*`, `~`, `$HOME` and variants); not overridable |
| 2 | `always_deny[]` | regex, case-insensitive by default |
| 3 | `always_confirm[]` | forces the card back even if allowed below |
| 4 | `always_allow[]` | regex |
| 5 | `tools.<name>.default` | per-tool |
| 6 | global `default` | ships as `confirm` |

Pattern-capable tools are `terminal`, `edit_file`, `write_file`,
`delete_path`, `move_path`, `copy_path`, `create_directory`, `fetch`,
`search_web`, `skill`, and MCP tools as `mcp:<server>:<tool>`. The legacy
boolean `always_allow_tool_actions` still exists, marked pre-v0.224.0.

For an external agent that has its own permission system, Zed's **deny and
confirm still win**; the agent's own rules only apply where Zed would have
allowed the action. That is the right default for a host, and it is exactly
the question PiCode will face the day it drives a guest CLI.

### A4. Profiles bundle model plus tools

A profile is `{name, tools{}, context_servers{}, enable_all_context_servers,
default_model}`. Three ship: **Write** (read, edit, run commands), **Ask**
(read-only), **Minimal** (no project tools); `write` is the default. The
selector sits in the composer, beside token usage, so the choice is made per
message rather than buried in settings. Profiles decide *availability*;
the permission table decides *allow, deny or confirm*. Two separate axes,
which is why neither grows modes.

This is the same shape as the 2026-09-17 launch-presets study, arrived at
independently, and it is a point in favour of that plan.

### A5. Terminal Threads — the pattern closest to PiCode

Since May 2026, Zed has three thread kinds: **Zed Agent** (Zed's providers,
native tools, MCP), **External Agents** (an ACP process with its own auth),
and **Terminal Threads** — "the tool's command-line experience organized in
Zed", with the CLI's own auth and config. A bell from a terminal that is not
focused raises the same OS notification the agent uses; clicking it focuses
the terminal and clears the indicator.

That third kind is PiCode's Agent CLIs terminals, named as a first-class
thread type rather than a lesser fallback. It is evidence for the shape
ADR-0069 and ADR-0089 already chose: a CLI in a terminal is not a
second-class agent, it is its own kind, and the host's job is to organize
and notify rather than to impersonate.

### A6. Two things to copy that cost almost nothing

- **Notification values, not a boolean.** `notify_when_agent_waiting` is
  `primary_screen` (default) / `all_screens` / `never`, and fires both when
  a turn completes *and* when a tool needs confirmation.
  `play_sound_when_agent_done` is `never` (default) / `when_hidden` /
  `always`. "When hidden" is the value that makes a sound tolerable.
- **Compaction with a visible seam.** `agent.auto_compact` is
  `{enabled: true, threshold: "90%"}`, where the threshold takes a
  percentage string, a positive int (tokens used) or a negative int (tokens
  remaining). The compacted span stays in the thread as an expandable
  "Context Compacted" entry, and "New From Summary" starts a fresh thread
  from it. Compaction that hides its own seam is the version users distrust.

### A7. What Zed does *not* promise

Feature parity across external agents is explicitly disclaimed: thread
history, checkpoints and token usage "depend on the agent integration", and
steering is Zed Agent only. Profiles and Zed Skills do not apply to external
agents at all. Honest, and the same disclaimer PiCode's chips make today.

**Correction to an earlier read:** Zed's "text threads vs agent threads"
confusion, which 2026 reviews still repeat, no longer exists — Text Threads
were removed in v0.231.1 (2026-04-08) to streamline the agentic workflow.
There is no "Agent 1.0"; Zed itself hit 1.0 on 2026-04-29 and is on 1.20.1.

## B. The ACP trigger, re-measured

ADR-0091 refuses an agent-protocol client and names one undated trigger:
re-measure "when a single protocol (ACP or a successor) carries
**first-party, non-adapter** support across **most** of the CLIs PiCode
hosts". The 2026-09-03 study measured that and found adapters almost
everywhere. Nineteen days later the answer is different, so this section
re-measures it against the nine CLIs in `internal/clipkgs/specs.go`.

The registry index (`registry.json`, release `v2026.09.22-a3f02fa`) carries
**41 agents** today; `zed.dev/acp` lists 47 names, six of them not in the
registry. JetBrains IDEs consume the same registry natively since 2025.3.2;
VS Code only through a third-party extension.

| # | PiCode CLI | ACP today | Maintainer | Verdict |
|---|---|---|---|---|
| 1 | **Pi** | `pi-acp` 0.0.33, spawns `pi --mode rpc` | community (one author), MIT | **adapter** — first-party declined |
| 2 | Claude Code | `@agentclientprotocol/claude-agent-acp` over the Claude Agent SDK | **Anthropic** + Zed + JetBrains | adapter, vendor co-maintained |
| 3 | Codex CLI | `@agentclientprotocol/codex-acp`, starts the Codex App Server | **OpenAI** + JetBrains + Zed | adapter, vendor co-maintained |
| 4 | Grok Build | `grok agent stdio`, native over stdio | **xAI** | **first-party** |
| 5 | Hermes Agent | `hermes acp`, native | **Nous Research** | **first-party**, not in the registry |
| 6 | OpenCode | `opencode acp`, native (`src/acp`) | **Anomaly** | **first-party** |
| 7 | Muse Code | third-party wrappers only | community | none |
| 8 | Antigravity | `antigravity-acp` 1.1.1, Google-signed binary | **Google LLC** | **first-party** |
| 9 | Omp | `omp acp`, native, permission-gated writes | **upstream** | **first-party**, not in the registry |

**Five of nine are first-party and native.** Seven of nine have the vendor's
name on the implementation. Two have nothing a vendor stands behind: Muse
Code, and — the finding that matters — **Pi**.

Pi's maintainer closed the first-party ACP pull request in January 2026 with
a reason, not a shrug: Zed "don't support their own protocol in full months
after release", so an ACP mode "should be built as a project separate from
pi-mono, possibly on top of rpc mode". The re-ask in discussion #4444 has run
from May to September 2026 with no maintainer decision.

### What that inverts

ADR-0091 reasoned that ACP was adapters of uneven depth and that it "adds
nothing for pi" because pi already speaks RPC to PiCode. Both halves are
still true, and together they now point the other way:

- For **Pi**, ACP remains pointless. PiCode has pi's RPC, which is what the
  community adapter wraps anyway. Nothing to gain, ADR-0003 untouched.
- For the **guests**, the thing ADR-0091 accepted as the price — "PiCode
  cannot drive guest CLIs: no permission answering, no headless sessions, no
  composer for them" — is now purchasable from the vendors themselves for
  five of the eight, and from vendor-co-maintained adapters for two more.

So the honest reading is that the trigger has fired *for the population it
was written about*, while staying irrelevant for the one agent PiCode
manages. Whether "most of the CLIs PiCode hosts" means five-of-nine native
or seven-of-nine vendor-backed is the owner's call, and so is whether to
re-open the decision at all. **This study does not supersede ADR-0091.** It
records that the named trigger's condition is now arguably met, with the
receipts, and stops there.

### What re-opening would cost, honestly

A protocol client is not a weekend. From Zed's own disclaimers: thread
history, checkpoints and token usage vary per agent, so PiCode would own a
capability matrix and the empty states for every gap. Auth stays the
vendor's — Zed says plainly that an API key configured for its own agent
does not configure Claude Agent. Five of the nine would each need a launch
path, and two of those are not in the registry at all. Against that: the
permission cards, the composer and the headless runs that ADR-0089's prompt
door approximates today with a bracketed paste and an honest "Sent to the
terminal, not: the model saw it".

## C. The feel bar — measure it or drop the claim

Zed's engineering posts have real receipts: GPUI targets a **8.33 ms frame
budget** at 120 fps, and the Metal work reports frame times "consistently
under 4 ms". Its *comparison* pages do not: "<1s startup", "~600MB RAM",
"<10ms typing latency" against VS Code, with no methodology. The
third-party numbers echoed across 2026 review sites (0.60 s startup, 222 MB,
2 ms latency) come from posts that name neither hardware nor method, and
there is counter-evidence — a Typometer run in 2024 put Sublime ahead, a
Windows user in December 2025 reported 6–10 s first starts, and Zed's own
input-latency issue #26900 sat in `needs repro`.

**The lesson is the discipline, not the numbers.** Zed decided what one
frame is allowed to cost and then measured against it. PiCode's equivalent
line, `benchmarks.md:127` — "interactions respond in <100ms" — has never
been measured and nothing in `make ci` can fail because of it. Today's
build, for the record:

| Artifact | Raw | Gzip |
|---|---|---|
| `browser/assets/index-*.js` | 3.4 MB | 1.0 MB |
| `browser/assets/subset-shared.chunk-*.js` | 1.8 MB | 0.7 MB |
| whole `browser/` build | 15 MB across 138 files | — |

A megabyte of gzipped JavaScript before the first frame is not a scandal for
a local tool, but it is unbudgeted, and an unbudgeted number only moves one
way. Two cheap gates would make the Feel bar honest:

1. **A bundle budget in `ci-gates`.** Record today's gzip size per entry;
   fail when it grows past a threshold the owner sets. This is a script and
   a checked-in number, not a dependency.
2. **One latency probe.** Keystroke to echo through websocket plus tmux,
   p95 over a few hundred keys, on the scratch instance. It is the one
   number a terminal product cannot fake, and `benchmarks.md:127` is
   currently a promise about it.

Neither needs an ADR. Both need a `docs/handoff/open/performance.md` to own
them, which does not exist today.

## What PiCode adapts

| # | Borrow | From | Cost | Why it earns its place |
|---|---|---|---|---|
| 1 | **Turn summary above the composer** — *6 files · +142 −38* plus basenames | A1 | low | E4 already knows the turn's files; this is the line that makes a six-card turn legible |
| 2 | **Follow the agent** — one toggle, editor pane jumps to each touched file | A2 | low | both halves exist and nothing joins them; the most visible item here |
| 3 | **Cross-file review pane** — every hunk of the turn in one scroll, Keep / Undo per hunk, plus Keep all and **Undo last reject** | A1 | med | the real gap: review is per-card today, so "what did this turn do" has no answer |
| 4 | **Notification values, not a boolean** — `never` / `when hidden` / `always`, firing on both turn-end and needs-you | A6 | low | matches the tier-1 sensors PiCode already has |
| 5 | **Visible compaction seam** — an expandable "Context Compacted" entry and a threshold in percent or tokens-remaining | A6 | med | `docs/handoff/open/compaction.md` exists; this is the UI half |
| 6 | **Permission precedence as a decision table** — deny > confirm > allow > per-tool > global, with the host's deny winning over a guest's own rules | A3 | — | costs nothing today and is the table to write *before* any guest-control work, not after |

Items 1, 2 and 4 are independent of the ACP question and can ship whenever.
Item 3 is the one that changes the product's feel. Item 6 is a paragraph to
write now so the decision is not invented under pressure later.

## What PiCode refuses

| Temptation | Why not |
|---|---|
| Edit prediction, LSP, outline, vim mode | ADR-0015 and the diff-editor roadmap: we are not a worse IDE. CodeMirror stays the file widget |
| CRDT collaboration, channels, multiplayer buffers | Zed's own reviewers call this its differentiator *for teams sharing an editor*; PiCode's unit is an agent in a workspace |
| Copying Zed's comparison numbers | no methodology, contradicted by independent runs; quoting them would break "honesty over polish" |
| A GPU renderer or a frame-budget claim | PiCode is a browser client; the budget to own is the terminal echo, not the frame |
| Shipping an ACP client on this study's say-so | ADR-0091 is the owner's decision; this note supplies evidence, not a mandate |
| A second thread concept (Zed's removed Text Threads) | the one thing Zed took back out; do not add it |

## Open questions

1. **For the owner:** does "most of the CLIs PiCode hosts" mean five-of-nine
   native or seven-of-nine vendor-backed, and does either re-open ADR-0091?
2. If it re-opens, does Pi stay on RPC while guests speak ACP — two protocol
   paths in one product — or does that asymmetry itself argue for waiting?
3. Hermes and Omp ship ACP but are absent from the registry, so a registry
   view would miss them. Does a PiCode integration follow the registry or
   the binaries it already manages?
4. What is the bundle threshold in gate 1, and is a p95 terminal echo number
   worth a scratch-instance fixture in CI, or a periodic manual run?
