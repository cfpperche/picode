# Study: AGENTS.md across the nine CLIs — who reads what, and what PiCode can manage

**Date**: 2026-09-23 · **Asked by**: the owner ("now that Claude also adopts
AGENTS.md, research references and find features PiCode can add to manage the
repository's AGENTS.md — first find out whether every PiCode CLI supports it").
**Decision**: none yet; the options are in §7 and the owner's questions in
[`docs/handoff/open/agents-md.md`](../handoff/open/agents-md.md).
**Method**: every CLI is installed on this machine and was measured at the
version in §2. Loaders were read where the code ships (Pi, Omp, Hermes,
OpenCode's bundle, Claude Code's binary); `grok inspect --json` and Hermes's
own manifest ran on sentinel fixtures; three cheap model probes (Claude Code on
Haiku twice, Omp on its default flash model once) settled what only a run
could. Everything else is vendor documentation, marked as such; third-party
claims are marked secondary.

## 1. Why now

Claude Code has read `AGENTS.md` since 2.1.277 (2026-09-18). With it, the
answer to the first question is **yes, all nine read it**. But no two of
them read it the same way. PiCode knows which CLIs a person runs, in which folder
and worktree, and where each CLI keeps its session records. No other tool in the
stack has that view, so PiCode is where the question "what will each of my agents
actually read here?" can be answered.

**Imports are not portable.** `@path` expands in Claude Code (four hops, docs)
and Omp (five, code), and Antigravity expands a Markdown link to the file with
an `@` in front of it (embedded docs).
No import syntax is documented for Codex, OpenCode, Grok or Muse, and the Pi and
Hermes loaders have none (code). **Five of the nine read an import line as
plain text.**

Third-party guides put Antigravity's cap at 12,000 characters. The docs inside
1.2.9 say 24,000 bytes.

## 3. Five differences that shape the design

### 3.1 Which file wins in one folder

When a repository has both files, each agent gets different instructions and
nobody chose that:

| `AGENTS.md` and `CLAUDE.md` both present | Reads |
|---|---|
| Claude Code | `CLAUDE.md` only (default mode) |
| Codex, OpenCode, Pi, Muse Code | `AGENTS.md` (Codex reads `CLAUDE.md` only as a configured fallback name) |
| Hermes | the `AGENTS.md` chain; `CLAUDE.md` only when there is none, and never with a `.hermes.md` |
| Grok, Omp | both |
| Antigravity | `AGENTS.md` (with `GEMINI.md`); never `CLAUDE.md` |

### 3.2 Personal files

Codex, Pi and Hermes read `AGENTS.override.md`. Claude Code ignores it (docs)
and so does Grok (measured). Claude Code and Grok read `CLAUDE.local.md`. For
Claude it counts as a `CLAUDE.md`, so someone who adds one for private notes
switches `AGENTS.md` off for themselves alone. Claude's docs give the fix:
`instructionFiles: claude-md-and-agents-md`.

### 3.3 Worktrees: PiCode's own layout (measured)

PiCode's worktree actions create worktrees inside the repository, at
`<repo>/.worktrees/<name>` (`internal/gitcmd/gitcmd.go:137`). This repository's
own process does the same (`make worktree`). The fixture:

- the main checkout's `AGENTS.md` says `MAIN-CHECKOUT`;
- the copy in `.worktrees/wt` says `WORKTREE-BRANCH`;
- for Omp only, an `AGENTS.md` in the folder that holds the repository says
  `ABOVE-REPO`.

Every run started from inside the worktree:

| CLI | Read from `<repo>/.worktrees/wt` | Receipt |
|---|---|---|
| Pi | the worktree's file only | `loadProjectContextFiles` run |
| Claude Code | the worktree's file only, for `AGENTS.md` and for `CLAUDE.md` | the probe transcripts' `Contents of …` lines |
| Grok | the worktree's file only | `grok inspect --json` |
| Hermes | the worktree's file only | `list_context_file_sources` |
| **Omp** | **all three: the folder above the repository, the main checkout, the worktree** | probe on `zai/glm-5.3-flash` |
| Codex, OpenCode, Muse Code, Antigravity | bounded at the repository or worktree root by their docs or code; not run | — |

So an Omp agent on a branch in a PiCode worktree reads main's `AGENTS.md` and
the branch's copy together. If the branch is the one changing `AGENTS.md`, the
agent gets both versions at once. It also reads any `AGENTS.md` in a folder
between the repository and home, such as `~/code/AGENTS.md`. Pi already fixed
this upstream: the comment on `findShadowedContextFile` describes this exact case
("the main repo's context file that a nested linked worktree's own copy
shadows").

### 3.4 Size: this repository's AGENTS.md (329 lines, 21,149 bytes)

| CLI | Limit | This repository's `AGENTS.md` |
|---|---|---|
| Hermes | 20,000 characters on a small-window model | **truncated** at a 64k-token window, whole at 200k (manifest, measured) |
| Antigravity | 24,000 bytes per file | 88% of the cap |
| Codex | 32 KiB for the whole chain | 65% |
| Claude Code | "target under 200 lines" | 329 lines |
| Pi, Omp, OpenCode, Grok, Muse Code | none documented or found | — |

Only Hermes warns when it truncates, and its warning names the file. The other
CLIs give no sign from inside the session.

### 3.5 Gates

- **Trust.** Grok and Muse Code ignore a project's instructions until the folder
  is trusted. Measured for Grok: the same fixture listed zero project files when
  untrusted and six when trusted.
- **Injection scan.** Hermes blocks a file its prompt-injection scan flags.
- **Claude Code.** It reads no `AGENTS.md` on Bedrock, with telemetry disabled,
  or in the first session after an upgrade.

To the user, every one of these looks like "the agent ignores AGENTS.md".

## 4. On this machine

- **36 git repositories** under the home folder (depth 4, worktrees and tool
  folders excluded): 24 have no instruction file, 6 have `AGENTS.md` only, 5
  have both, 1 has `CLAUDE.md` only.
- **Of the 5 with both files, 3 tell Claude in plain prose to read `AGENTS.md`.**
  The other 2 use the `@AGENTS.md` import. Claude's docs single out the prose
  pattern. Because a `CLAUDE.md` exists, Claude's own `AGENTS.md` loading is off
  in those repositories, and Claude "sees AGENTS.md only if it decides to open
  the file". Every other CLI reads `AGENTS.md` there; Claude Code alone may not.
- **31 Claude Code sessions** since 2026-09-19 logged `agents-md: no CLAUDE.md
  found; AGENTS.md loaded: /home/goat/picode/AGENTS.md`. The feature is live
  here, and all 31 sessions started at the main checkout.

## 5. How others manage instruction files

| Product | What it does with instruction files | What PiCode takes |
|---|---|---|
| Hermes `/context` | a per-file manifest: status, token estimate, and why a file did not load | the status vocabulary |
| Grok `grok inspect --json` | discovered files with scope, bytes, tokens, trust, and which foreign sources are on | a machine-readable answer before any launch |
| Claude Code | `/memory` and `/context` "Memory files"; `instructionFiles` in four modes; `claudeMdExcludes`; `/init` reads other tools' files; `/import` appends a one-time copy of `AGENTS.md` to `CLAUDE.md`; a table for retiring old workarounds | the fix wording; the warning that copies drift |
| Codex | `/init`; `/import` from Claude Code and Cursor turns their instructions into `AGENTS.md`, handpicked, "review imported setup before you rely on it"; `project_doc_fallback_filenames` | fallback names as a Settings row |
| Gemini CLI | `/memory show`, `/memory reload`; the footer counts loaded context files; `context.fileName` takes a list | the count at a glance |
| VS Code | an Agent Customizations editor scoped to the selected harness; Instructions with **New** (workspace or user); validation; each response's References list the instructions used; Agent Debug Logs; `chat.useAgentsMdFile`, `chat.useNestedAgentsMdFiles`, `chat.useClaudeMdFile` | per-harness scope, which is PiCode's per-CLI column |
| Cursor | Customize → Rules; `/create-rule`; `AGENTS.md` at the root and nested; Team → Project → User order | — (a rules format of its own) |
| Zed | the first match among nine names (`.rules` … `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`); the Rules Library became Skills plus a personal `AGENTS.md` | evidence that the personal layer converges on `AGENTS.md` |
| Kiro | steering files with inclusion modes (always, fileMatch, manual, auto); a Generate Steering Docs button; `AGENTS.md` always included | — (the modes are Kiro's own) |
| Conductor | Repository Settings keep host-owned preferences per action (general, review, PR, fix errors, conflicts, branch names) beside checked-in files | refused for now (§9) |
| opcode | a `CLAUDE.md` editor with preview, and a scanner that finds every `CLAUDE.md` across projects | the scanner, not the editor |
| ruler, rulesync | one source folder generates each vendor's file; ruler's CI checks that the copies still match | refused (§9) |
| agents-lint 0.5.0 (MIT) | stale paths, missing npm scripts and make targets, deprecated packages, old framework patterns, conflicts across files; a 0–100 freshness score | the stale-reference finding |
| AgentLinter (MIT) | eight scored dimensions aimed at agent-workspace files (`SOUL.md`, `openclaw.json`) | — (little for repositories) |
| Factory Agent Readiness | `AGENTS.md` is one signal among 100+; `/readiness-fix` proposes one | — |
| Omp `compress` | rewrites a text file into a dense prompt register and reports what it drops | a possible action on the size finding, where Omp is installed |

**The one controlled study.** Gloaguen et al., *Evaluating AGENTS.md: Are
Repository-Level Context Files Helpful for Coding Agents?* (ETH Zürich, arXiv
2602.11988, February 2026, revised June 2026):

- context files "do not generally improve task success rates, while increasing
  inference cost by over 20% on average";
- "repository overviews … are not helpful";
- the instructions are followed, and are useful "for specifying non-standard
  coding practices";
- "any attempts to improve performance should be rigorously evaluated before
  deployment".

Secondary coverage splits the result into −3% for LLM-generated files and +4%
for developer-written ones. The abstract does not state that split.

## 6. Seven patterns that converged

1. **Show the file's fate, not just the file.** Hermes and `grok inspect`
   answer per file: loaded, truncated, shadowed, blocked, untrusted. VS Code
   lists the instructions each response used. An editor that only opens the
   file answers the wrong question.
2. **One source, and bridges instead of copies.** Claude's docs prefer
   `@AGENTS.md` to a copy. Zed replaced its Rules Library with a personal
   `AGENTS.md`. ruler and rulesync generate copies and then need CI to catch
   drift. Both vendors' `/import` commands make one-time copies, which start
   drifting the next day.
3. **The personal layer is separate and never committed**: `CLAUDE.local.md`,
   `AGENTS.override.md`, and the user-level files in Zed, Codex and Claude.
4. **Scope by folder; the closest file wins.** agents.md says so, and Codex,
   Grok, Muse Code and Hermes's chain agree.
5. **Size is a budget, and a cut is announced.** Hermes warns, Antigravity
   demotes the overflow to a pointer, Codex caps bytes, Claude sets a 200-line
   target.
6. **Generation produces a draft.** Every vendor ships an `/init`. The one
   controlled study found no general gain and a real cost. Kiro and Cursor
   generate into files that a person reviews.
7. **Trust gates project instructions**: Grok and Muse Code, and Claude for
   imports from outside the folder.

## 7. What PiCode adapts — options for the owner

### 7.1 The engine: declared, never inferred

The engine is one resolver with a declaration per CLI, in the shape
`internal/climemory/specs.go` already uses (ADR-0163: a tier is declared, never
inferred). Each declaration lists:

- the file names, in order;
- the walk rule and where it stops;
- the personal and global files;
- the limits, gates and import syntax;
- for every field, where it was read and at which version.

A CLI with no declaration answers "unknown", never a guess. Each declaration is
pinned by a sentinel-fixture test like the ones in §3.3. What PiCode can know
about each CLI falls into three tiers:

| Tier | CLIs today | What PiCode shows |
|---|---|---|
| `observed` | Claude Code (transcript `Contents of <path>`), Codex (rollout `# AGENTS.md instructions for <dir>`), Grok (`prompt_context.json`) | what a session actually read, from the vendor's own record |
| `listed` | Grok (`grok inspect --json`) | the vendor's own answer before launch, with no model call |
| `predicted` | Pi, Omp, OpenCode, Hermes, Muse Code, Antigravity — and every CLI before launch | the declared rule, applied by PiCode |

Hermes's manifest exists only inside a running session, so from outside,
Hermes is predicted.

### 7.2 The options

| Option | What it is | Boundary | Verdict |
|---|---|---|---|
| **A. Instructions, read-only, per workspace** | a matrix of instruction files in the tree (root and nested) against the CLIs (the installed ones by default); each cell a status (reads, shadowed by X, truncated at N, not read, needs trust); a folder picker for monorepos; findings below, one line and one action each; opening a file goes to the existing editor (`#/file/w/<id>/<path>`) | none: reads files and vendor records on demand and stores nothing (the Memory pane's rule) | **first** |
| **B. At creation** | when a workspace and a CLI are picked in the Create dialog, one line such as "Claude Code reads CLAUDE.md here; AGENTS.md is shadowed", with the fix | none | with A: it is the moat — users control their agents from the moment of creation |
| **C. Settings declarations** | Claude `instructionFiles` (user scope, `pluginConfigs["agents-md@builtin"].options.instructionFiles`); Codex `project_doc_max_bytes` and `project_doc_fallback_filenames`; Hermes `context_file_max_chars`; OpenCode `instructions`; Omp `disabledProviders` | none: the settings engine's existing door (ADR-0163) | small; any time |
| **D. What this agent read** | a line on the agent, in the Inspector rail, from the `observed` tier: the files and their git revision at session start | none | after A |
| **E. Fixes that write into the repository** | replace a prose pointer with `@AGENTS.md` (diff before write); add a personal file together with its `.gitignore` line; start the CLI's own `/init` (or `muse init`) as an agent through the prompt door, never PiCode-generated text | **persistence**: PiCode writes files in the user's repository, the same line the omp study drew for its Project pane | one ADR, after the owner's yes |
| **F. Measure the effect** | the exit record (ADR-0194) keeps the instruction files' git blob ids at launch; Outcomes compares resolved rates before and after an `AGENTS.md` change, with n | **persistence**: a field in the exit snapshot, so an ADR-0194 amendment | after A, once exits carry the field |
| **G. Upstream** | an Omp issue on nested-worktree shadowing, citing Pi's `findShadowedContextFile` | none | now; the owner files it |

**How this relates to the omp study's Project pane** (its option B,
`2026-09-22-omp-helpers-placement.md` §5): that pane would need the same engine.
The workspace view comes first because `AGENTS.md` belongs to the repository,
not to one CLI. A per-CLI pane can later show one column of the same matrix.

## 9. What PiCode refuses

| Temptation | Why not |
|---|---|
| A second editor for `AGENTS.md` | the Files view already edits text; a pane with its own editor becomes a second writer |
| A PiCode-owned rules store, fanned out to each vendor's file (ruler or rulesync inside PiCode) | copies drift and need CI to catch it; PiCode writes the vendor's own file and never keeps a second source of truth (ADR-0129, ADR-0150); eight of the nine read `AGENTS.md` natively, and the ninth takes an import |
| Generating `AGENTS.md` with PiCode's own prompt | the controlled study found no general gain, over 20% added cost, and no help from overviews; the vendor's `/init` runs as an agent the person watches and edits |
| Writing vendor trust files (`~/.grok/trusted_folders.toml`) | trust is the person's security decision; PiCode explains why nothing loads and opens the CLI's own prompt |
| Re-implementing Hermes's injection scan | a second scanner would disagree with the one that decides; PiCode reports Hermes's own verdict, and only when it is observed |
| Symlinks as the default bridge | Claude's docs: on Windows a symlink needs Administrator rights or Developer Mode, and Git checks it out as text; PiCode ships a Windows desktop shell |
| Host-owned instructions outside the repository (Conductor's per-action preferences) | an instruction no other tool can see is an invisible system prompt; if wanted later, it is a decision of its own |
| Applying findings automatically | the exit-feedback study's rule: a person approves before behaviour changes |

## 10. Open questions for the owner

1. **The door for A.** A workspace tab beside Files and Git (one per
   repository, like `#/git/…`), a section in the Inspector rail, or a tenth CLI
   pane showing one column? Recommendation: the workspace tab. A CLI pane can
   read the same engine later.
2. **Order.** Read-only first (A–D, no ADR) and writes later (E, one ADR), or
   both together?
3. **Worktrees.** File the Omp issue (G), and warn in the Create dialog when an
   Omp agent starts inside `.worktrees/`? Moving PiCode's worktrees out of the
   repository would remove the problem for every CLI, but it is a large change
   (`internal/gitcmd`, this repository's own process), and four of the five CLIs
   run were not affected.
4. **Trust.** Only explain ("Grok won't read this folder's instructions until
   you trust it") and open Grok in a terminal, or also offer to write the trust
   file? The second is a security-model decision.
5. **Exit records (F).** Should they carry instruction revisions, and captured
   at launch or at removal?
6. **This repository's own `AGENTS.md`.** Hermes truncates it on small-window
   models, and it is 329 lines against Claude's 200-line target. Trim it, split
   it into nested files, or accept it? It is the operating contract, so this is
   the owner's call.
