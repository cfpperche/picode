# 2026-09-21 — inbox-cli: `picode inbox notify|ask`, the Inbox door for any guest CLI

`cmd/picode/inbox.go` (+ dispatch/usage): `picode inbox notify --title T [--body B] [--reason R]`
files an FYI and prints the item id; `picode inbox ask --question Q [--context C] [--wait] [--timeout D]`
files a blocking question — without `--wait` it prints the id and returns, with `--wait` it
prints "waiting for your answer in the Inbox…" to stderr once and polls `GET /api/inbox/{id}`
every 2 s, printing `mcptool.AnswerLine(item.response)` on stdout when done (404 →
"answered/removed elsewhere", exit 0; `--timeout` elapses → one stderr line, exit 1; no default
timeout). Discovery: `--url` > `PICODE_URL`/`PICODE_TERM_URL` > server.json, re-read per poll
(daemon rebinds); token + loopback-TLS rules reused from `internal/mcptool`. Identity
(ADR-0134): `PICODE_AGENT_ID` → agent, `PICODE_TERM_ID` → terminal, else system + `user@host`.
Payload shape copies pi-inbox's `buildNotifyPayload`/`buildAskPayload` exactly (tests pin it).

Respond-handler finding (the assignment's step-investigation): the 409 gap IS real, but not
where the route's terminal row sits — a terminal whose pi is gone already records + closes
(ADR-0154 N1, `AnswerTerminalQuestion`). The real gap is **system-sourced** questions (a guest
outside PiCode): `RespondAndForward` returned `ErrNoReplyChannel` → 409/toast refusal, item
stayed open forever, and BOTH answer surfaces refused — the route and, decisively, the Inbox
app's own respond action (`internal/apps/inbox.go`), which is where humans actually click
Reply. Fix at both call sites (the store keeps its conservative contract, matching the N1
precedent): on `ErrNoReplyChannel`, record via `RespondInboxItem` (stored + done + 200 /
"Answer recorded" toast) and append `apps.InboxAnswerRecordedNote` correcting the store's
"reply not delivered" annotation. Agent-exists→task-queue, terminal-hosts-pi→receiver,
agent-interactive, and agent/terminal-gone rows are byte-identical (pinned by existing tests).
