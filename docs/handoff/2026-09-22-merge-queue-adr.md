# 2026-09-22 — merge-queue-adr: the machinery adopts the community standard
The owner asked what the repository's own benchmarks say about delivery, and whether we were inventing a machinery the community already standardized. They do, and we were. `docs/benchmarks/2026-09-21-delivery-governance.md` — written a day before ADR-0182 and never cited by it — prescribes "reuse provider governance" (t3code row) and names the limit on the GitHub merge-queue row ("provider eligibility and merge-group CI configuration constrain direct reuse"). `docs/plans/delivery-flow.md` goes further: no generic shell-command executor, no mandatory GitHub/PR workflow, no replacement CI/CD platform, and projects may use different integration providers. D3 slices 1-3 had built PiCode's own runner as the engine anyway — and the runner is, precisely, that generic executor.
**ADR-0186** (accepted in session) redirects it: the integration declaration names its mode, `provider` or `local`; under `provider` PiCode enqueues through the project's own queue (the repository's GitHub merge queue, or a reviewer's `r+` where bors runs) and observes it — present, position, ejected with the provider's reason — never merging by itself, with the provider's CI validating the merge result and `order` refused because the provider owns it. `local` keeps the runner as a *mode*, the fallback for a repository with no hosting provider. The engine is declared, never detected: a project that declares nothing is still not executed, because absence is a named blocker.
Vocabulary follows the standard — merge queue, entry, position, approved, integrating, integrated, ejected with a reason — in the architecture doc now and in the Delivery view's lane when it is built. Internal store names keep their own words; the mapping is written down.
No code changed in this branch: the store, the doors and the runner stay as landed. The next slice is the mode itself, then the provider path.
