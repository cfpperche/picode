# 2026-09-07 — feat/term-find: find inside a terminal pane

Shipped: phase 2 of the pane menu. `Ctrl+Shift+F` (or **Find…** in the menu)
floats a field over the terminal — never resizing the pane, so tmux gets no
SIGWINCH and the guest TUI does not redraw — highlighting every match,
counting them (`3/14`), walking them with Enter / Shift+Enter; Escape closes
and returns the keyboard. Files: `components/TermFindBar.jsx`,
`lib/termFind.js` (pure + 4 tests), `lib/appKeys.js` (`app.terminal.find`),
the `find` row in `lib/termMenu.js`, the addon on the entry in `ShellTerm.jsx`.

New dependency `@xterm/addon-search@0.16.0` — published in the same minute as
the `@xterm/xterm@6.0.0` / `addon-fit@0.11.0` already here (0.17 betas want
xterm 6.1). Its decorations reach xterm's proposed API, so `xtermOptions()`
(shared, so mobile too) now sets `allowProposedApi`; when a terminal lacks it
the counter says "Unavailable" instead of a plausible "No results".

The chord is not VS Code's Ctrl+F on purpose: the shifted family is already
this terminal's (Ctrl+Shift+C/V), the plain chord stays with `less`/`vim`/
readline, and Ctrl+F still opens the browser's find outside a pane.

Verified: `make ci-scoped` green (338 JS tests). Live on scratch `find`
(:8472), shell terminal with 14 matches: `1/14`, Enter → `2/14` → `3/14`,
Shift+Enter → `2/14`, every match decorated, pane stays at 32 rows with the
field open, Escape clears decorations and refocuses, `Ctrl+Shift+F` reopens,
plain `Ctrl+F` opens nothing. One defect found and fixed there: the addon
threw on proposed API and the field said "No results" over 14 matches.

visual-review: PASS (find-open, find-empty; overlayAudit ok, `[data-align-row]`
36×5 after moving the counter onto the control height; card 5/5).

Debts: no case-sensitive / regex / whole-word toggles (the addon supports
them); Find is desktop only — the mobile terminal has no menu to open it.

Merge: fast-forward ready.
