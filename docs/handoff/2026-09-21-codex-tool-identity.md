# 2026-09-21 — codex-tool-identity: a Codex agent's tools answered `no identity`
Found by exercising the delivery tool from real vendor sessions (the open half of the delivery-flow debt): **Codex starts a stdio MCP server with an empty environment**, so every one of PiCode's tools answered `no identity` for a Codex agent — Delivery, Browser, Computer, Inbox and Checklist alike. Measured with an env probe: the shell inside the agent's terminal carried `PICODE_AGENT_ID`/`PICODE_TERM_ID`, the server spawned by `codex exec` carried none. Claude Code and OpenCode hand the environment over and were unaffected.
Fixed: a Codex launch now writes the identity into each server's own config — `-c mcp_servers.<name>.env.PICODE_TERM_ID`, `PICODE_AGENT_ID` when the terminal is bound, `PICODE_TERM_URL` and `PICODE_DATA` (`toolIdentityEnv` in `internal/server/cli_tools.go`); the plan preview names the same values with `{terminal}`/`{agent}`/`{url}`/`{data}` placeholders, and the shared `codexToolArgs` keeps the preview and the real launch from drifting. `PiCode · Delivery` also joined `ToolPresets()`, so every family in the catalog has a connector card (`TestEveryToolFamilyHasACard`).
Verified end to end: on a scratch built from this branch, a Codex agent's `codex exec` — run with the `-c` flags taken from PiCode's own generated `launch.sh` — declared a delivery with `principal` equal to the agent id, and the Git ▸ Delivery read shows `agents: ["CodexFix2"]`. Decision-table rows cover the identity present, absent, and OpenCode's config staying free of it.
Vendor sessions so far: **Claude Code** (headless with PiCode's `--mcp-config`, and driven through PiCode's own prompt door), **Codex** (failed before, passes after), **OpenCode** (its MCP children do inherit, so nothing to fix; its default model is outside the owner's plan, so no live call was made). Grok, Hermes, Muse and Omp were still being probed by a parallel sweep when this branch closed; what it found belongs in the delivery-flow debt, not here.
