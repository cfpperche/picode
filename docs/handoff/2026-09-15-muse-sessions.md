# 2026-09-15 — muse-sessions: Muse Code sessions from the launcher index

Task: the owner asked for Muse Code sessions then Antigravity sessions, in sequence; this is the Muse half.
Shipped: Muse Code has no adapter (surface: terminal), so it had no Sessions tab. Meta's launcher keeps ~/.local/share/muse/session-index.db (or $XDG_DATA_HOME/muse/session-index.db) with a sessions table carrying session_id, title, first_user_prompt, workspace_root, model_id, prompt_count, created_at_us/updated_at_us and session_log_path — everything the picker needs. MuseSource (internal/clisession/muse.go) is a read-only SQL query with no log parsing. The resume flag is --resume <uuid> (verified with muse --help 1.2.1-R2847.1); Summary.ResumeArgs carries it and the existing launch-overrides path starts the terminal with it. Rows with no workspace or prompt_count 0 (the launcher's own empty sessions) stay out; a row with no timestamp at all is skipped because the picker orders by it. Source is list-only: no Reader/Writer, so Muse is neither handoff source nor target. cliPanes now adds Sessions from sessions.list instead of cap.integration (web/shared/domain/cliLaunch.js + its test).
Verified: on a scratch, GET /api/clis/muse/sessions returned the real session; the pane shows Launch | Terminals | Sessions with the row (model, 27m ago, 12 MB, 11 msgs, preview) and 'Open in terminal' produced a terminal whose launchApplied.args = [--resume, 01a0a2c3-174e-75e2-9b89-26da398d273b].
