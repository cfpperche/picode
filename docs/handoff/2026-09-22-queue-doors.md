# 2026-09-22 — queue-doors: the owner can act on the queue, and a project can say how it integrates
Slice 2a of D3, on top of the accepted ADR-0182. Two things landed:
**The owner's doors** — `POST /api/{workspaces|agents|terminals}/{id}/delivery/queue` carries the queue actions as `store.OwnerActor` (the store refuses `order` and `authorize` for anyone else, so a route that forgot to check cannot grant them), and the Delivery read now answers with `queue` plus the already-resolved `integration`, so no surface repeats the fallback.
**The declaration** — `GET|PUT /api/delivery/integration` writes "how this project integrates": `ffOnly` plus up to eight single-line commands, one row per scope, resolved workspace-first with the machine as the fallback layer and a built-in default (`ffOnly`, no checks) when neither declares. `?workspace=nope` is refused rather than writing a row nobody reads.
Also fixed while testing: an entry enqueued *for* a delivery belongs to whoever **declared** it (the owner may write it down on an agent's behalf; the agent keeps the right to withdraw), which the store now reads from the delivery row instead of taking the actor's name.
Tests: the door walk (enqueue → order → authorize → start → finish with a refusal at each wrong turn — second active entry, note on a shape that forbids it, start before authorize, stale version, unknown entry), the read's payload, the declaration round-trip and its fallback (workspace beats machine, machine beats nothing), four shape refusals, the store's own layer/version tests, and a row in `TestEveryMutationAppendsAnEvent`.
Next in the slice: the agent's own door (request/withdraw through the delivery tool contract, which means the CLI, MCP and pi-package faces together), then the serialized executor, then the lane in the Delivery view.
