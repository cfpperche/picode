# 2026-09-19 — "this page is not answering" (feat/annot-bridge)

Owner: the strip's own warning fired with a chip saved on the page — so the
push channel (page `postMessage` → shell → app) was dead, and my previous
fix (re-subscribe) was not the whole story.

## Two changes, one guaranteed
1. **Settings at creation.** `SetIsWebMessageEnabled(true)` was called when
   the mode was armed — after the document existed. It moved to
   `apply_scripts` (webview creation, beside `SetIsScriptEnabled`), so every
   document is born with the channel on.
2. **A pull door that cannot be dead.** `btab_annotate_state` returns the
   page's state through `ExecuteScript`'s *return value* (host→page→host on
   the command's own result: no page-side bridge involved). The strip polls
   it every 1.5 s while the mode is on; `postMessage` stays the fast path.

## Evidence
- Harness, real page + real keys: the pull expression returns
  `{kind:"state",count:1,items:[…]}` with styles and rect; after Esc in the
  page it returns `{"kind":"off"}`; with no handle `""`. Rust 15/15 (incl.
  guards that the pull is wired on both sides), JS 13/13 on the annotate
  file, test-js green, `make desktop-shell` cross-build green.
- New command artifacts all present (handler, manifest, capability,
  autogenerated permission, regenerated schemas).
